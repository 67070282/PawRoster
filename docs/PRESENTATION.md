## เตรียม Demo

เปิด Browser สอง session ที่ cookie ไม่ร่วมกัน (เช่น normal/incognito) เป็น A และ B ในบ้านเดียวกัน เพิ่มอีกบัญชี C บ้านอื่นเพื่อแสดง isolation ใช้ข้อมูลสังเคราะห์ทั้งหมด เตรียมงานสองรายการ “ให้อาหารมื้อเย็น” และ “เปลี่ยนน้ำ” และหน้าผลทดสอบ/architecture

### Happy Path

1. A เพิ่ม “โมจิ” และงานให้อาหาร กำหนดเวลาที่เข้าใจง่าย เปิด B แล้วกดอัปเดต ต้องเห็นงานเดียวกัน
2. A รับงาน → ทั้งสองหน้าหลังอัปเดตเห็นชื่อ A
3. A กดทำแล้ว กรอก note → มุมมอง “งานทั้งหมด” เห็นสถานะ done, เวลา และ note ประวัติมี created/claim/complete
4. restart app หรือ recreate โดยคง volume → งานและประวัติยังอยู่

### Failure Cases

1. ทั้งสองเปิดงาน “เปลี่ยนน้ำ” ขณะยัง open, A รับก่อน, B กดรับจากหน้าเก่า → B เห็นข้อความ conflict และรายการล่าสุด ไม่มี claim ซ้ำ
2. เปิด C บ้านอื่น → ไม่เห็นงาน A; เปิด automated test R5 เพื่อยืนยันการเดา task ID ถูกปฏิเสธด้วย 404
3. กรอกข้อมูลว่าง → UI validation; automated R6 ครอบคลุม API validation และ JSON เสีย
4. หยุด app แล้วกดอัปเดต → แจ้งเชื่อมต่อไม่ได้ เริ่ม app ใหม่แล้วอัปเดตอีกครั้ง

ไม่ใช้ `down -v` ใน Demo เพราะลบข้อมูล และไม่ใช้ screenshot แทนการตรวจระบบจริงเมื่อกรรมการขอดู

## คำถามที่สมาชิกต้องตอบได้

- ทำไมสองคนรับงานเดียวกันไม่สำเร็จทั้งคู่? transaction ตรวจ state และเขียนกับ audit ในหน่วยเดียว
- ข้อมูลคงอยู่ที่ไหน? SQLite file ใน named volume ไม่ใช่ writable layer ของ image
- บ้านอื่นเดา ID ได้ไหม? ทุก query เชื่อม home_id จาก session ที่ server
- UI เก่าแล้วจะเกิดอะไร? API ส่ง 409, UI โหลดใหม่และแจ้ง error
- ทำไมไม่ใช้ Kafka/LLM? ไม่จำเป็นต่อ requirement นี้ เพิ่ม failure mode โดยไม่เพิ่มผลลัพธ์หลัก
- ระบบรู้ได้อย่างไรว่าสัตว์ได้รับการดูแลจริง? ไม่รู้ เป็นบันทึกจากสมาชิก ไม่ใช่ sensor หรือหลักฐานทางการแพทย์
- AI ช่วยอะไร และทีมตรวจอย่างไร? เปิด AI disclosure, code และ tests แล้วอธิบายส่วนที่ตน review จริง
