# ข้อเสนอโครงงาน PawRoster

## 1. Problem Statement

กลุ่มเป้าหมายตั้งต้นคือบ้านที่มีผู้ดูแลสัตว์อย่างน้อยสองคน เมื่อต่างคนใช้แชตหรือความจำ อาจไม่รู้ว่าใครจะทำงาน และใครทำแล้ว อาการคือถามซ้ำ ทำซ้ำ หรือไม่มีคนรับผิดชอบ สาเหตุที่ตั้งสมมติฐานคือไม่มีสถานะงานร่วมที่เชื่อมผู้รับผิดชอบกับการบันทึกผล

**สถานะหลักฐาน:** เป็นสมมติฐานออกแบบ ยังไม่มีผลสัมภาษณ์หรือแบบสอบถาม และไม่อ้างจำนวนบ้านที่มีปัญหาหรือความถี่ของเหตุการณ์จริง กติการายวิชาระบุธีมและมาตรฐานระบบ แต่ไม่ได้เป็นหลักฐานยืนยันปัญหานี้

แผนตรวจสมมติฐาน: สัมภาษณ์ 5 บ้านที่มีผู้ดูแลหลายคน ขอความยินยอมและไม่เก็บชื่อจริง ถามวิธีแบ่งงาน เหตุการณ์ล่าสุดที่ไม่รู้ว่าใครทำแล้ว และความถี่ใน 7 วันที่ผ่านมา บันทึกวันที่ จำนวนตัวอย่าง วิธีคัดเลือก และข้อจำกัดในรายงาน เมื่อได้ผลแล้วจึงปรับ Problem Statement โดยบันทึกการเปลี่ยน scope

## 2. Solution และขอบเขต

สถานะร่วม `open → claimed → done` แสดงคนรับงานและเวลาทำเสร็จ เปลี่ยนสถานะผ่าน Backend ภายใน transaction ผู้รับงานคืนงานได้เป็น `claimed → open` งานที่เสร็จแล้วไม่เปิดกลับ เพื่อคงความหมายของประวัติ

หนึ่งรายการหมายถึงหนึ่งครั้งของการดูแล ระบบกัน **การรับและยืนยันรายการเดียวกันซ้ำ** ไม่ได้ป้องกันสมาชิกสร้างงานสองรายการที่มีความหมายเหมือนกัน และไม่รับรองว่าเจ้าของกดเสร็จตรงกับการดูแลจริง

ข้อแลกเปลี่ยน: เลือก HTML/CSS/JavaScript + Node.js + SQLite เพื่อลดภาระติดตั้งและมี transaction จริง เหมาะระบบขนาดเล็กแบบหนึ่ง instance; ไม่เพิ่ม broker หรือ LLM เพราะไม่จำเป็นต่อ flow นี้

## 3. Target Users

| ผู้ใช้ | บริบท | สิทธิ์ |
|---|---|---|
| ผู้เริ่มบ้าน | ต้องการแบ่งงานให้สมาชิก | สร้างบ้าน รับรหัสเชิญ เพิ่มสัตว์และงาน |
| สมาชิกบ้าน | ช่วยดูแลตามตาราง | เห็นข้อมูลในบ้าน เพิ่มสัตว์/งาน รับงาน และเปลี่ยนงานที่ตนรับ |
| ผู้ดูแลระบบ | รันบริการและเก็บสำรอง | เข้าถึงเครื่อง/volume ตามสิทธิ์โฮสต์ ไม่มีบัญชี admin ใน UI |

ผู้สร้างบ้านกับสมาชิกมีสิทธิ์ในแอปเท่ากัน รุ่นนี้ไม่รองรับการเชิญแบบหมดอายุ การถอดสมาชิก หรือการย้ายบ้าน จึงเหมาะทีมผู้ดูแลที่ไว้ใจกัน

## 5. Social Impact & Assessment

Output: จำนวนงานสร้าง/รับ/เสร็จที่ตรวจจากฐานข้อมูล Outcome ที่ต้องศึกษาต่อ: ลดเวลาถามว่าใครทำ และลดงานไม่มีคนรับ ไม่ตีความจำนวน click ว่าเป็นสุขภาพสัตว์ที่ดีขึ้น

เก็บ baseline 7 วันด้วยสมุดบันทึก แล้วทดลอง 7 วันในกลุ่มเดิม นิยามอัตรางานเลยเวลา = งานที่ไม่มี completed_at ภายใน due / งานที่ถึงกำหนดทั้งหมด ใช้ DB export ที่ลบข้อมูลระบุตัวบุคคลก่อนวิเคราะห์ เป้าหมายทดลองตั้งต้นลดอัตรานี้ลง 20% เทียบ baseline โดยเป็น **เป้าหมาย ไม่ใช่ผลลัพธ์ที่พิสูจน์แล้ว** ปัจจัยกวนคือชนิดงาน ปริมาณงานและการเปลี่ยนพฤติกรรมเพราะรู้ว่าถูกศึกษา

ความเสี่ยง: ผู้ใช้กดเสร็จทั้งที่ยังไม่ทำ, รหัสเชิญหลุด, พึ่งระบบมากเกินไป, อุปกรณ์ไม่มีอินเทอร์เน็ต บ้านต้องยังสื่อสารกันเมื่อระบบขัดข้อง และไม่ใส่ข้อมูลรักษาหรือข้อมูลอ่อนไหวใน note

## 7. Sustainability & Unfair Advantage

แนวทางเริ่มต้นเป็นแอป self-host สำหรับบ้านหรือกลุ่มอาสาขนาดเล็ก ไม่มีค่าบริการ API โมเดลที่อาจศึกษาคือองค์กรอาสาสนับสนุนค่า hosting แต่ยังไม่ยืนยัน willingness to pay ค่าใช้จ่ายจริงต้องคำนวณจาก hosting/backup/เวลาบำรุงรักษา ณ วันเสนอ

ยังไม่มี unfair advantage ที่พิสูจน์ได้ แนวทางสร้างคือความรู้จากการทดลองกับผู้ดูแลและการปรับ workflow ตามข้อมูลที่ได้รับความยินยอม ไม่อ้างว่าใช้ AI หรือมีฐานข้อมูลเฉพาะเป็นข้อได้เปรียบในรุ่นนี้

Roadmap: ตรวจผู้ใช้จริงและ Jenkins แล้วตรวจ commit รุ่นส่งใน Course Container อีกครั้ง → invitation expiry/member removal/account deletion → recurring tasks → notification ที่มี retry/fallback โดยต้องปรับ acceptance criteria ก่อนเริ่มแต่ละส่วน
